# Как снимались цифры

Все замеры сделаны на одном ноутбуке: Intel AX201 (iwlwifi), Wi-Fi 5 ГГц,
сигнал −22…−25 дБм, ядро 7.2 (Omarchy 4). Результат у вас будет другим,
методика ниже.

## Всплески задержки

Пинг до роутера, 200 пакетов с интервалом 0,2 с, без другой нагрузки на
канал. Считается число ответов дольше 20 мс.

```bash
ping -i 0.2 -c 200 192.168.1.1
```

| Состояние | Всплесков >20 мс | Максимум |
|---|---|---|
| `power/control=auto` (два замера) | 16 и 11 | 202 и 205 мс |
| `power/control=on` (два замера) | 0 и 1 | 11 и 50 мс |

Переключается так (нужен root):

```bash
echo on   | sudo tee /sys/class/net/wlo1/device/power/control
echo auto | sudo tee /sys/class/net/wlo1/device/power/control
```

Тот же эффект без root даёт поток мелких пакетов. Ниже `auto` и разная
частота, по 150 пингов:

| Поток на роутер | Всплесков >20 мс | Максимум |
|---|---|---|
| нет | 7–17 | 189–203 мс |
| 10 Гц | 9 | 100 мс |
| 25 Гц | 8 | 36 мс |
| 50 Гц | 3 | 40 мс |
| 100 Гц | 0 | 11–15 мс |

Поэтому в `netmode keepalive` 100 пакетов в секунду.

## Несколько соединений

```bash
netmode get https://proof.ovh.net/files/10Mb.dat -o a.bin -n 1
netmode get https://proof.ovh.net/files/10Mb.dat -o b.bin -n 16
sha256sum a.bin b.bin
```

24,1 с против 5,3 с, суммы совпали. Сервер Cloudflare для проверки не
подходит: он не отдаёт диапазоны, и `netmode get` честно качает одним потоком.

## Скорость одного соединения с видеосервера

Файл `video2.cdnlibs.org//uploads/converted_videos/anime/10393/players/1983/1983_2160.mp4`
(1 039 099 724 байт), заголовок `Referer: https://animelib.org/`.

Одно соединение, диапазон от 100 МБ, Мбит/с по секундам:
`0, 8, 24, 22, 22, 21, 19, 21, 17, 12, 14, 7, 4, 6, 4, 5, 4, 2, 3, 3`.
Четыре соединения: быстрый старт, потом около 12–15 суммарно. Соединение,
открытое на 18-й секунде, когда первое уже остыло: 65, 40, 67, 40, 37, 40…
Значит, ограничение у каждого соединения своё.

Короткие куски по 8 МБ, шесть параллельных соединений, каждый кусок на новом
соединении, 40 секунд: в среднем 120 Мбит/с, минимум по секундам 18. Часть
свежих соединений всё же оказывается медленной (медиана куска 2 с, хвост
7–23 с), поэтому прокси сбрасывает кусок, если за 2,5 с он прошёл меньше
запланированного.

Сквозная проверка (`chromium --headless=new`, чистый профиль, расширение,
прокси, HTTPS-страница на localhost с `<video>` и `playbackRate = 3`):

| | позиция видео через 90 с | ждал данных | кадров / пропущено |
|---|---|---|---|
| напрямую | 185 с | 16 из 45 замеров | 4443 / 883 |
| через прокси | 260 с | 2 из 46 | 6246 / 1064 |
| через прокси с запасом 160 МБ | 263 с | 1 из 45 | |

Пропуски кадров в обоих случаях связаны с программным декодированием 3×
4K в headless-режиме без GPU и к сети не относятся.

## Битрейт серии

`ffprobe -show_entries packet=pts_time,size` по всем 34813 пакетам файла:
в среднем 5,6 Мбит/с, медиана 4,3, 90-й процентиль 12,7, 99-й 23,1,
максимум 27,8 Мбит/с. Секунд выше 15 Мбит/с 93 из 1452, выше 25 — 8. Самое
тяжёлое окно в 10 секунд даёт 24,9 Мбит/с (с 1346-й секунды). Самые большие
кадры около 950 КБ.

Программное декодирование самых тяжёлых 30 секунд (`ffmpeg -ss 1335 -t 30
-f null -`): 7,0 с при 4 потоках и 5,6 с при 8, то есть запас в 4–5 раз.

## Запас в памяти

С открытым диапазоном от 300 МБ и чтением в темпе 5,6 Мбит/с прокси через 10
секунд держит 158 МБ впереди плеера и дальше остаётся около 200 МБ (160 запас
плюс ещё не вытесненное). Время до первого байта при перемотке 1,0–2,3 с,
при чтении из уже скачанного места 0,00 с.

## Что не помогло

- Сменить DNS на Cloudflare. Это полезно само по себе (запрос без кэша
  с 125 до 8 мс), но к рывкам видео отношения не имеет.
- Искать другой адрес видеосервера AnimeLib. `video1.cdnlibs.org` и
  `video2.cdnlibs.org` у всех резолверов отдают один и тот же адрес.
- Отключить QUIC. Он работает (проверено на Google и cloudflare-quic.com).
